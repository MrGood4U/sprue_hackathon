# Frontend Implementation Status

Updated on 2026-09-12 after adding x402 transaction pagination, HashScan evidence links, and active per-request price display.

## Current Baseline

The existing ten route-level pages are the product frontend and will be developed in place. Shared UI, navigation, tokens, localization, and page ownership carry forward. Dashboard, Wallet and Access, Model Service, Agent Planner, Builder, API, and X402 use authenticated live workspace APIs and never fall back to sample data; only the public product retains the explicitly temporary backend demo runtime. API exposes real managed deployment, private export/test, and a confirmed stop action. X402 renders real publication, recipient, ledger, and paid-request facts, activates an exact HBAR price, and offers a separately confirmed stop action. Pending and failed mutations remain visible, and the browser never receives the internal API credential used for paid delivery. Creator routes still require a configured Privy session, and empty or failed reads remain explicit.

The Creator Console keeps a workspace-scoped in-memory cache of resolved product identity while the authenticated application shell remains mounted. Dashboard loads, product-detail reads, creation, and renames refresh that cache; deletion removes both the ID and slug keys. Agent, Build, API, and X402 therefore reuse the real product name synchronously when switching tabs while continuing their normal live reads. Cached Dashboard summaries remain presentation-only and never replace backend authorization or freshness checks.

The Agent trace includes `semantic_entity_retrieval` between Graph discovery and model entity selection, followed by `semantic_field_retrieval` between entity selection and feasibility. The field stage embeds every field in the selected entities, reports provider batches and local cosine calculation, and persists the count of per-requirement alternatives retained for the model. Stages 2–9 now persist bounded, allowlisted `details_json` evidence and expose it in one-at-a-time expandable conversation cards: semantic output and search terms, source requirements, Graph discovery facts, formal aggregate rankings and decisions, raw entity rankings and selections, and requirement-level field alternatives. Actual embedding similarity is rendered as a decimal advisory rank only when the embedding provider produced it; deterministic evidence has no invented score. Empty aggregate or fallback paths remain explicit. The progress rail stays compact and uses the same backend events. Embedding failures map to explicit localized recovery guidance; no browser timer fabricates batch or completion progress.

Implemented browser behavior includes route navigation, explicit selection among English, Simplified Chinese, Spanish, French, German, Korean, and Japanese with a local preference, page composition, dialogs, Graph access-mode selection with API-key-only credential disclosure and a colocated credential action, backend-provided DAG inspection, and backend action flows. Authenticated feature hooks select live backend clients; the public route alone selects the demo runtime. Build and request flows run through feature hooks with cancellation and duplicate-submission protection; no authenticated product page imports browser fixture records.

The live Dashboard now places an accessible trash icon in each product row. Activating it opens a named second-confirmation dialog; Cancel receives initial focus, deletion shows an in-progress state, and failures remain visible and retryable in the dialog. Confirmation fetches the current product lock version and calls the authenticated idempotent delete endpoint. Only backend success removes the row. The backend stores a soft-delete tombstone and excludes it from ordinary product reads and new Agent work without destroying historical evidence.

The Wallet and Access page now renders the complete authenticated workspace wallet address and copies it through the browser Clipboard API with a temporary-textarea fallback plus accessible success or failure feedback. The Base Sepolia funding address and canonical Hedera account ID each have an adjacent copy control with independent four-second feedback and a success icon. Authenticated bootstrap idempotently ensures one Privy Ethereum wallet owned by the verified Privy user and binds it to the stable Sprue user/default workspace. The page reads the current Base Sepolia USDC balance directly from Privy through the backend, persists a balance observation, and shows an unavailable state rather than a fake zero or sample value when provider data cannot be read. A `Settings` action opens a focused dialog for a required positive, six-decimal USDC limit per UTC day. If no current signer observation exists, Privy's visible delegated-action flow runs first; the backend then records the signer/policy reference as pending and unverified, without fabricating a signer secret reference, and atomically records or replaces the local Sprue daily budget as draft. Authorization and budget statuses stay separate, and the copy explicitly excludes creator-confirmed transfers. The saved draft limit is durable and idempotent, but signer-secret binding, provider-policy verification, and the live delegated Graph purchase path remain gated. Graph API-key mode lists redacted workspace credentials and saves new write-only keys through AES-256-GCM backend storage; x402 mode hides that section without deleting saved keys. Each non-revoked credential now has an explicit validation action, one active credential can be selected as the workspace default for future source planning, and deletion requires confirmation before revoking access and destroying encrypted key material. Validation discloses its one minimal provider query and gives per-row loading/result feedback. No raw key is retained in frontend state after successful submission or returned by the API. If no Hedera testnet account maps to the Privy EVM address, the HBAR card shows an explicit creation button. The button disables with a spinner during the owner-authorized command, exposes accessible busy/error feedback, and replaces itself with the canonical Hedera account ID and live Mirror Node HBAR balance after reconciliation. It never submits an address from the browser or activates during page load. The creator-confirmed Privy EVM signing spike succeeded on Hedera testnet, completed the mapped account, and spent only its network fee. The temporary test control and feedback UI have been removed. The backend now projects verified control and HBAR spend capability when Mirror Node reports a complete account at the same bound Privy EVM address. Direct creator withdrawals are implemented for the fixed Base Sepolia USDC contract and Hedera testnet HBAR through Privy's visible confirmation UI. Exact integer-unit validation, chain and asset allowlists, HBAR account-ID conversion, duplicate-submit protection, submitted/confirmed/reverted feedback, network evidence links, and backend balance refresh are included. A known zero balance keeps the transfer entry point operable and opens an explanatory read-only modal, while an unavailable observation remains disabled. User rejection never causes an automatic retry. Durable withdrawal records, delegated Sprue spending execution, native Hedera x402 signing, mainnet use, and publication remain fail closed.

The Model Service page provides visible, validated fields for a full HTTPS OpenAI-compatible Chat Completions URL, an API key, and an exact model name. Its API key is concealed by default behind a closed-eye control; configured secret state is rendered as stars. Empty fields show the official OpenAI Chat Completions URL and `gpt-5.6-sol` as examples. The key is sent only to the backend, never stored by the frontend, and never returned. The backend stores one owner-authorized profile per workspace and encrypts its key with AES-256-GCM before PostgreSQL; a server-only versioned keyring supports restart-safe reads and controlled key rotation. A secondary connection test sends one minimal fixed request with current form values, may reuse the saved workspace key when the key field is blank, and does not save the form or return provider content. The next explicit Agent plan uses the configured model; other actions do not trigger extra model calls. Explicit profile deletion/revocation, exact durable planning-call audit binding, provider allowlisting, and distributed rate limiting remain unimplemented.

The Agent Planner no longer mounts the demo runtime. It resolves the route slug to a workspace-owned PostgreSQL product, displays its actual `original_intent`, reopens the newest durable Agent session, and reads ordered user/assistant messages. The active conversation selects only the newest user message and its following assistant result; confirming a replacement run immediately swaps the earlier visible cards for the newly submitted intent and live trace without deleting any durable message or trace record. A newly created blank draft has no synthetic user bubble: the first non-empty submission both records the durable message and initializes `original_intent`, while later submissions remain conversation revisions. Before the first run, creators can either generate with the Agent or navigate directly to Build without creating a session or invoking a provider. Failed, cancelled, clarification, and unsupported terminal results retain the same manual Builder escape route; an active run hides it, while a compilation-ready proposal replaces it with `Review DAG`. A submission creates an idempotent session/message command, resolves the encrypted saved model and selected active Graph key only on the server, and runs a bounded three-stage source-exploration harness: the first model stage defines semantic requirements and search terms, the second selects only candidate/query-entity references from compact summaries, the Harness expands fields for those validated selections from its trusted schema snapshot, and the third model stage binds exact fields and proposes the registered-operator DAG. Official DeepSeek planning stages use its Responses Structured Outputs contract (`text.format.type=json_schema`) with bounded real reasoning; other OpenAI-compatible profiles use one `submit_sprue_plan` function call. Every response is revalidated with the full Zod schema. At most one schema-repair request is shared across the three stages inside the four-call ceiling, and each provider call has a 16,384-token output ceiling. Each external model or Graph step now defaults to a ten-minute timeout, while the whole run has a separate one-hour default deadline; both are configurable within reviewed maxima and the run deadline cannot be shorter than a step timeout. The browser submission timeout exceeds the maximum backend run, cursor polling remains active throughout long work with bounded adaptive backoff, and unmounting cancels both the submission and polling. The active trace also exposes its exact command ID so a confirmed in-flight stop action can request same-process cooperative server cancellation; the original handler then persists a terminal cancelled result. The harness appends sanitized trace events while it runs; the browser renders every observed stage as a stable conversation card that updates from running to complete or failed. Completed conversations reproduce those cards from the newest assistant message's persisted trace. The UI shows the real model name, candidate Subgraph/network, manifest CID, query entity, observed activity metadata, limitations, registered-operator counts, deterministic validation summaries, and the persisted total duration on completed or failed replies, including hour-level labels for long runs; durations below one second are labeled explicitly instead of being rounded to zero. It deliberately does not expose hidden chain-of-thought. The current result is honest source feasibility, not a compiled product: immutable Deployment IDs, exact mappings, coverage, access binding, and durable source snapshots are blockers, so the automatic review link is withheld, while manual creation remains explicit. Queue-backed execution, cross-instance cancellation recovery, SSE, proposal acceptance/history selection, source admission, and compilation remain pending.

The Builder now includes the first editable workflow slice under `src/features/workflow-editor/`. It supports a select tool, a hand tool, node dragging, typed connections, node and edge deletion, undo/redo, zoom and fit-to-view, operator and template insertion, operator-specific configuration forms, client-side structural validation, and a centered modal node inspector with a dimmed backdrop. The compact editor toolbar and bounded template/operator palette are mounted in React Flow's top-center and top-left panels, visually floating above the canvas without consuming separate layout rows or columns. The former workflow-name, node-count, and draft-status summary strip has been removed. The canvas now uses a larger, higher-contrast dot grid through the dedicated DAG grid token so spatial alignment remains legible without competing with nodes or lineage edges. A single click selects a node or edge in select mode and enables toolbar/keyboard deletion; hand mode reserves canvas interaction for panning and keeps the grab cursor consistent over empty canvas, nodes, ports, and edges while leaving floating controls unaffected. A double click opens a temporary node-edit buffer with explicit Confirm and Cancel actions. Palette labels are single-line with mouse-following and keyboard-focus descriptions, without a native duplicate tooltip, and operator icons are visually distinct. Canvas nodes show only their icon, name, and status. The Source editor keeps discovered-source selection, live existing-Subgraph search, and direct Graph-identifier verification in one modal; verified schema evidence is inserted atomically into the planning draft without exposing the workspace credential to the browser. Builder no longer mounts the demo runtime: it resolves the current product route, loads the newest durable Agent run, and projects the server-owned `builderDraft` with real validated candidates, query entities, field bindings, operator nodes, and edges. Failed or absent proposals create an empty workflow, not sample data. Edits auto-cache for the current browser session under workspace/product/proposal identity and survive tab navigation; a newer Agent result invalidates the older copy. `Save draft` reports this browser-session boundary. `Run backend build` now submits the exact layout-free working DAG to an authenticated read-only compiler. Its disabled rotating state prevents duplicate requests; success caches the current browser draft and opens API, while semantic or request failure preserves the graph and opens a bounded issue dialog. The compiler validates graph topology, ports, input cardinality, acyclicity, single-output reachability, exact operator versions/configurations, Source normalization boundaries, predecessor-derived schemas, and the declared output contract. Source admission, durable product-version save, GraphQL compilation, data execution, deployment, and revision-conflict handling remain unimplemented, and the returned compilation hash is not durable build evidence.

Application metadata, entry-page actions, and project instructions identify Sprue as a product. The demo workspace and simulated financial operations remain labeled with their actual behavior.

### Creator Authentication Slice, 2026-09-07

The Creator Console now loads the public Privy app identifier, exposes separate Google and GitHub choices, restores the provider session through the SDK, retrieves an access token in memory, and sends it as a Bearer credential to the backend bootstrap route. Creator `/app` routes fail closed until authentication and bootstrap complete; `/p/*` remains public. Once bootstrap completes, `/login` immediately navigates to `/app` and does not render a signed-in confirmation card. The backend validates the token through Privy's server SDK, resolves its subject through `auth_identities`, and transactionally reuses or creates the stable Sprue user UUID, default workspace, and owner membership. Multiple explicitly linked provider identities can resolve to one user, but linking and conflict UX remain unimplemented and no heuristic merge occurs. Authentication does not create, fund, synchronize, or delegate the separate account wallet. Automated tests use injected provider verification and isolated PostgreSQL. A local Google sign-in and bootstrap was user-observed on 2026-09-07; repeatable GitHub and evaluator-host evidence remain pending.

The current Privy frontend dependency tree reports 27 production advisories: 25 moderate and two high. A non-breaking `npm audit fix` was applied, but the remaining findings are transitive through the supported Privy, WalletConnect, Coinbase, and MetaMask packages. The suggested forced remediation would downgrade the selected Privy SDK and is not accepted without compatibility review. Recheck upstream releases and the audit report before evaluator deployment; this is an open dependency risk, not evidence that the authentication flow is production-ready.

### Graph Source Discovery Update

Graph source exploration now uses a checked-in projection of every mainnet and testnet entry advertising the Subgraphs service in The Graph Networks Registry v0.7.119 (65 networks). CAIP-2 identity, official labels, Graph network IDs, aliases, and network type share one backend source of truth. It derives independent per-network SourceNeed records, verifies 30-day activity for every bounded candidate, and progressively inspects ranked schemas with a separate budget per need so one network cannot consume another network's inspection allowance. Candidate selection precedes multi-source operator composition inside the second structured model stage. Authorized bounded data probes, automated registry refresh, and canonical source admission remain pending.
