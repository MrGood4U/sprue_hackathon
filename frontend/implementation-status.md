# Frontend Implementation Status

Updated on 2026-09-07 after removing service-fee and retained-evidence presentation from the hackathon Monetization page.

## Current Baseline

The existing ten route-level pages are the product frontend and will be developed in place. Shared UI, navigation, tokens, localization, and page ownership carry forward. The public Entry page keeps its `Log in` and `Enter console` actions separate from provider selection; signed-out creator actions navigate to the dedicated Login page. The frontend now loads its evaluator workspace projection, Agent trace, DAG, product metadata, API response, wallet display state and consumer action result from the backend demo runtime. Creator routes require a configured Privy session; Google and GitHub login actions use their official brand marks, feed one backend-verified account/bootstrap path, and redirect directly from Login to the Dashboard after bootstrap. Authenticated identity is exposed through one top-right account avatar in every Creator Console header rather than a competing sidebar block. Its anchored menu shows the verified account label and current workspace, keeps non-action profile text selectable without accidental dismissal, links only to existing Dashboard, Wallet & Access, and Model Service routes, and separates sign-out from navigation. Language and account controls are top-aligned at the shared right edge, while the Dashboard's product-creation action is grouped with the `All products` toolbar. Product names share a controlled inline editor between the Dashboard and product header; the evaluator new-product action assigns `New Product`, and name changes are retained only in backend process memory for the current demo session. The public product remains accessible without creator login. Agent planning and DAG review are separate product views under one product header. Other live backend integrations and the complete durable MVP remain unfinished.

Implemented browser behavior includes route navigation, English/Simplified Chinese selection with a local preference, page composition, dialogs, Graph access-mode selection with API-key-only credential disclosure and a colocated credential action, backend-provided DAG inspection, and backend action flows. `services/index.js` selects the backend demo client. Build and request flows run through feature hooks with cancellation and duplicate-submission protection; no product page imports browser fixture records.

The Wallet and Access page now renders the complete Base Sepolia Graph-funding address and copies it through the browser Clipboard API with a temporary-textarea fallback plus accessible success or failure feedback. The redundant `View wallet` action is removed. The backend demo projection exposes Graph-funding USDC and Hedera x402-revenue HBAR as separate network- and account-labeled balances, and each balance has a colocated `Transfer out` entry point. The transfer dialog is intentionally fail-closed: destination and amount submission remain disabled and balances remain unchanged until M5/E1 define and implement provider signing, fee quoting, idempotent submission, and settlement reconciliation.

The Model Service page provides visible, validated fields for a full HTTPS OpenAI-compatible Chat Completions URL, an API key, and an exact model name. Its API key is concealed by default behind a closed-eye control; configured secret state is rendered as stars. Empty fields show the official OpenAI Chat Completions URL and `gpt-5.6-sol` as examples. The key is sent only to the backend, never stored by the frontend, and never returned. The evaluator runtime retains a saved profile only in bounded process memory under a random browser-session identifier and clears it on API restart. A secondary connection test sends one minimal fixed request with the current form values, may reuse the saved session key when the key field is blank, and does not save the form or return provider content. The next explicit Agent plan uses the configured model; other actions do not trigger extra model calls. Durable workspace ownership, provider validation policy, rate limiting, and secret-manager persistence remain unimplemented.

The Builder now includes the first editable workflow slice under `src/features/workflow-editor/`. It supports a select tool, a hand tool, node dragging, typed connections, node and edge deletion, undo/redo, zoom and fit-to-view, operator and template insertion, operator-specific configuration forms, client-side structural validation, and a centered modal node inspector with a dimmed backdrop. The compact editor toolbar and bounded template/operator palette are mounted in React Flow's top-center and top-left panels, visually floating above the canvas without consuming separate layout rows or columns. The former workflow-name, node-count, and draft-status summary strip has been removed. The canvas now uses a larger, higher-contrast dot grid through the dedicated DAG grid token so spatial alignment remains legible without competing with nodes or lineage edges. A single click selects a node or edge in select mode and enables toolbar/keyboard deletion; hand mode reserves canvas interaction for panning and keeps the grab cursor consistent over empty canvas, nodes, ports, and edges while leaving floating controls unaffected. A double click opens a temporary node-edit buffer with explicit Confirm and Cancel actions. Palette labels are single-line with mouse-following and keyboard-focus descriptions, without a native duplicate tooltip, and operator icons are visually distinct. Canvas nodes show only their icon, name, and status. The Source editor now keeps discovered-source selection, existing-Subgraph search, and direct Graph-identifier lookup in one modal. The discovery forms are explicitly unavailable and cannot confirm a source until the live Graph adapter and verification path are implemented. The current draft is projected back into the existing Builder evidence and Structured DAG views; disconnected or invalid output paths clear the derived schema and preview instead of presenting the old result as current. The `Save draft` control is an explicit demo-only UI boundary and reports that durable persistence is not connected; the backend durable version command and revision-conflict handling are not connected yet.

Application metadata, entry-page actions, and project instructions identify Sprue as a product. The demo workspace and simulated financial operations remain labeled with their actual behavior.

### Creator Authentication Slice, 2026-09-07

The Creator Console now loads the public Privy app identifier, exposes separate Google and GitHub choices, restores the provider session through the SDK, retrieves an access token in memory, and sends it as a Bearer credential to the backend bootstrap route. Creator `/app` routes fail closed until authentication and bootstrap complete; `/p/*` remains public. Once bootstrap completes, `/login` immediately navigates to `/app` and does not render a signed-in confirmation card. The backend validates the token through Privy's server SDK, resolves its subject through `auth_identities`, and transactionally reuses or creates the stable Sprue user UUID, default workspace, and owner membership. Multiple explicitly linked provider identities can resolve to one user, but linking and conflict UX remain unimplemented and no heuristic merge occurs. Authentication does not create, fund, synchronize, or delegate the separate account wallet. Automated tests use injected provider verification and isolated PostgreSQL. A local Google sign-in and bootstrap was user-observed on 2026-09-07; repeatable GitHub and evaluator-host evidence remain pending.

The current Privy frontend dependency tree reports 27 production advisories: 25 moderate and two high. A non-breaking `npm audit fix` was applied, but the remaining findings are transitive through the supported Privy, WalletConnect, Coinbase, and MetaMask packages. The suggested forced remediation would downgrade the selected Privy SDK and is not accepted without compatibility review. Recheck upstream releases and the audit report before evaluator deployment; this is an open dependency risk, not evidence that the authentication flow is production-ready.
