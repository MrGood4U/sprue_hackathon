# Wallet Module

Own account-wallet observations, policy/signature-grant references, funding views and authoritative Graph budget transactions. Consult sponsor/privy.md before provider work. Do not hold creator keys or imply user-enforced policy without evidence.

Status: account-wallet provisioning and the Wallet and Access read model are implemented. Authenticated bootstrap idempotently finds or creates one Privy Ethereum wallet owned by the verified Privy user, binds it to the stable Sprue user/default workspace, repairs an incomplete binding that lacks its active Base Sepolia address, and creates no signer or spending authority. Wallet/address binding is one atomic SQL statement with an explicit public-reference dependency, so absent network metadata cannot leave a new partial wallet row. Privy reads and the idempotency-keyed wallet-create request use one bounded retry for connection failures, timeouts, rate limits, and provider 5xx responses; authentication, authorization, validation, and other client errors fail immediately. Structured provider logs contain only operation, attempt, status category, delay, and recovery/exhaustion state, never credentials, provider bodies, user IDs, wallet IDs, addresses, or tokens. The read model fetches the current Base Sepolia USDC balance from Privy and appends its workspace-scoped observation. Missing provider data stays unavailable rather than falling back to sample values. The wallet-settings command reads a creator-approved delegated signer/policy reference from Privy, persists the signer observation as pending/unverified with no signer secret reference, and atomically stores one positive Base Sepolia USDC draft limit for the current UTC day. Repeating the same value is idempotent; changing it revokes the prior local policy. Provider authorization and the local budget remain separate records.

The Graph credential companion module stores API keys as AES-256-GCM ciphertext and exposes only redacted metadata to this read model. The explicit Hedera testnet activation command resolves only the authenticated workspace wallet's bound Privy EVM address, checks Mirror Node before submitting, sends at most one fixed-endpoint Portal faucet request, and reconciles uncertain results without another transfer. It persists the canonical account ID, HBAR capability observation, live balance snapshot, and synchronous control-command outcome. Portal credentials and wallet addresses are excluded from logs. A hollow account keeps control pending and spend capability false. After the creator-confirmed Privy EVM transaction demonstrated signing and fee spend on Hedera testnet, a complete Mirror Node account at the same bound EVM address is persisted as verified control with HBAR spend capability. Creator-confirmed outbound transfers exist in the frontend but have no durable server record. Provider-policy template verification, budget reservation/consumption, delegated Graph purchases, native Hedera x402 signing, and production provider controls remain reserved and fail closed; a saved local daily limit is not payment-execution evidence.
